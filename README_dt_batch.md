# Пакетный анализ Digital Twin 7.1 — `batch_analysis.py`

Прогоняет полный расчёт 7.1 для каждой пациентки из Excel-выгрузки клиники
(формат «отчет.xlsx»): `ivf_core.predict_single_patient` (L1–L6) и
`befe_batch_utils.compute_l7_posterior` (L7) — те же функции, что использует
приложение через `dt_bridge.py`.

```bash
python batch_analysis.py <input.xlsx> [output_dir] [--clinic "Название клиники"]
```

`RUN_BATCH.bat` делает то же для перетащенного на него файла и затем запускает
пост-обработку `dt_postprocess.py`.

## Что подаётся в модель

| Вход | Колонка выгрузки | Назначение |
|---|---|---|
| `age` | `Возраст` | возраст (обязательно) |
| `follicles` | `Количество фолликулов` | фолликулы на пункции |
| `known_okk` | `Число ОКК` | получено ооцитов |
| `known_mii` | `Число инсеминированных` | по указанию автора модели |
| `attempt` | `№ попытки` | номер попытки |

- **АМГ / КАФ** есть в выгрузке, но часто некорректны → по умолчанию в модель
  не подаются (`DEFAULT_AMH = 2.0`, `DEFAULT_AFC = 12`). Чтобы подавать их —
  `USE_REPORT_AMH = True` / `USE_REPORT_AFC = True` (с проверкой правдоподобия).
- **BMI** в выгрузке нет → `DEFAULT_BMI = 23.0`.
- **2PN, бластоцисты, хорошее качество, исход** в модель не подаются — они
  прогнозируются и сравниваются с фактом (предиктивная валидация).

Введённые ОКК и MII в 7.1 кондиционируют всю цепочку стадий (точное условное
распределение), а не просто подставляются в свою стадию.

**Пусто и 0.** Пакетные скрипты читают 0 и пустую ячейку одинаково — как
«неизвестно» (`opt_int`). Наблюдаемое отсутствие (например, 0 ооцитов) в пакетном
режиме не передаётся; для такого случая используйте `dt_bridge.compute`, где `0`
и `None` различаются.

## Выходные файлы

1. **`dt_analytics_data/dt_predictions.csv`** — схема `_save_analytics()` из
   `app.py` плюс колонки GNN: медианы и перцентили воронки, `p_per_transfer`,
   `p_overall_cycle`, байесовский posterior, KAT/NVSA, CSDI, GAT, кластер L4,
   OHSS, банкинг Esteves.
2. **`<output_dir>/OPU_table_filled_<время>.xlsx`** — формат OPU_table с колонкой
   `DIGITAL TWIN`.
3. **`<output_dir>/dt_vs_real_<время>.csv`** — прогноз против факта по каждой
   стадии и по исходу.
4. **`<output_dir>/batch_summary_<время>.csv`** — сводка по всем пациенткам со
   всеми слоями.

Все эти файлы содержат данные пациенток и в git не попадают (`.gitignore`).

### Колонка `DIGITAL TWIN`

Итоговая вероятность L7 (BEFE) **на один перенос**, рассчитанная на сценариях,
где есть что переносить. Если L7 недоступен, пишется `p_overall_cycle` —
механистическая вероятность L1–L4 за цикл; это другая величина, и в сводке её
нужно различать. Вероятность за цикл, согласованная с L7, и контракт «0 при
невозможном переносе» в пакетном режиме не вычисляются — они есть в приложении
и в `dt_bridge.compute`.

## Слои моделей: что активно

- **L1 воронка (NB + бета-биномиальные стадии), L2 FORTUNE+KPI, L4 кластер,
  байесовский posterior, Esteves** — чистый numpy/scipy, файлы моделей не нужны.
- **L3 KAT** — нужны `models/Prediction_KAN.pth`, `models/FTTransformer.joblib`
  (+ `KAT_ensemble_raw_weights.pth`, `isotonic_ensemble.pkl`) и `torch`. Без них
  KAT в L7 не входит, а в колонку `p_kat_raw` (определение 7.0 — среднее по всем
  сценариям) пишется прокси FORTUNE+KPI; источник видно в `nn_prediction.source`. Кодирование признаков
  FT-Transformer исправляется при запуске (`src/mambular_ple_fix.py`), как в
  клинической сборке.
- **L5 CSDI** — `models/embryo_v3_model/`; в L7 входит только внутри области
  обучения (`models/csdi_ood_stats.npz`).
- **L6 GAT** — `models/gnn_ivf_model.pt` и `torch_geometric`.

## Конфигурация (вверху `batch_analysis.py`)

`N_SIM = 2000`, `SEED_BASE = 42` (к нему прибавляется номер строки),
`DEFAULT_BMI`, `DEFAULT_AMH/AFC`, `USE_REPORT_AMH/AFC`, `SPERM_SOURCE`
(страта Esteves), `CLINIC_SUCCESSES/TRIALS` (батчи клиники для байесовского
posterior; на L7 не влияют), `DT_HEADLINE_COL` (запасная колонка для
`DIGITAL TWIN`), маппинг колонок `COL`.
