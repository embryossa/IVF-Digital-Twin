# Пайплайн тестирования и улучшения нарратора IVF Digital Twin

Стенд для регрессионной проверки локального клинического нарратора (Ollama,
`gemma4:12b-it-qat` / `medgemma1.5`) на CPU-машине. Исходный код обоих проектов
не изменяется — стенд только импортирует их модули.

## Зачем именно так

Нарратор DT устроен по принципу «Python классифицирует — LLM объясняет»
(`llm_consultant.py`). Значит проверять надо не «умную ли мысль высказала модель»,
а **соблюдает ли она контракт с пре-классификатором**: не переклассифицирует ли
метки, не изобретает ли числа, не приписывает ли число не тому полю, не назначает
ли лечение, не говорит ли о том, чего в контексте нет. Всё это — проверяемые
правила, а не вкусовщина, поэтому основная часть оценки детерминирована и
считается за миллисекунды без единого вызова LLM.

## Схема

```
fixtures.py      12 клинических сценариев (g-словари в формате globals app.py)
      │                 ↓ прогон через НАСТОЯЩИЙ llm_consultant.build_narrative_context()
      ├──────────► contexts.json      ← ровно тот JSON, который видит модель в проде
      │
run_eval.py      Ollama /api/chat со штатными _SYSTEM_NARRATOR и _build_messages
      │          (стриминг; резюмируемый — прерванный прогон продолжается)
      ├──────────► runs.jsonl         текст + prompt/eval токены + тайминги
      │
score.py         8 детерминированных метрик + штатный faithfulness.py
      ├──────────► scores.json
      │
run_variant.py   A/B: альтернативный системный промпт и/или сжатый контекст
compact_ctx.py   прототип сжатия контекста (короткие теги источников)
exp_cache.py     проверка переиспользования KV-кэша префикса
                 (в итоге не понадобился: вопрос закрыл лог сервера Ollama —
                  Gemma использует SWA, частичный префикс не переиспользуется)
probe.py         потоковый замер (видно tok/s во времени)
```

## Сценарии

Матрица покрывает не «типичных пациенток», а **места, где нарратор может сломаться**:

| id | что проверяет |
|---|---|
| S01 high_responder_ohss | высокий риск СГЯ + блок протокола, грейд A |
| S02 poor_responder_41 | низкий прогноз, риск пустого цикла, длительное накопление |
| S03 normal_baseline | базовая линия |
| S04 ood_dual_gradeC | вне распределения по двум подпространствам → грейд C |
| S05 ohss_lens_conflict | вероятностная и резервная оценки СГЯ расходятся |
| S06 wide_ci_disagreement | широкий ДИ + расхождение ансамбля |
| S07 sparse_no_befe | половины блоков нет — модель обязана молчать о них |
| S08 borderline_39_8 | 39.8% при границе категории 40% — соблазн округлить вверх |
| S09 neighbor_trap | BEFE «low», а GAT-аналоги оптимистичны — соблазн переклассифицировать |
| S10 banking_urgency | цепочка MII→эуплоиды, возрастная срочность |
| S11 no_protocol_block | нет AMH → блока протокола нет; любое «N МЕ» = галлюцинация |
| S12 obese_high_reserve | доза при ИМТ 38 — только из номограммы |

Сценарии — синтетические, но проходят через настоящий пре-классификатор, поэтому
метки (`prognosis_level`, `confidence_grade`, `OHSS_risk`…) вычисляются
продакшн-логикой, а не задаются вручную.

## Метрики

| код | метрика | что ловит |
|---|---|---|
| `grnd` | numeric_grounding | числа, которых нет в контексте |
| `BND` | label_binding | число ЕСТЬ в контексте, но приписано не тому полю (2PN назван «зрелыми ооцитами»); раздел аналогов сверяется отдельно — против профиля соседа |
| `RC` | reclassification | текст противоречит готовой метке (метка `low` → «высокие шансы») |
| `DIR` | directive_language | «показан», «назначить», «рекомендуется» — нарушение правила 3 |
| `NS` | null_safety | разговор о дозе/банкинге/аналогах, которых нет в контексте |
| `INF` | unsupported_inference | «это подтверждает», «это доказывает» — вывод сверх данных |
| `cov` | coverage | покрытие применимых разделов (неприменимые не штрафуются) |
| `LEAK` | leakage | `snake_case`-метки, think-теги, латиница в тексте врача |
| `F` | faithfulness | штатный `faithfulness.py`: утечка id утверждений и доза вне номограммы |

`SCORE` — инженерный светофор 0–100, не клиническая оценка: покрытие минус
взвешенные нарушения. Смотреть надо на столбцы, а не на итог.

## Как запускать

```bash
cd <стенд>
python fixtures.py                                   # пересобрать contexts.json
python run_eval.py --models gemma4:12b-it-qat --styles concise
python run_eval.py --plan                            # что осталось прогнать
python score.py                                      # таблица метрик
python run_variant.py --prompt v4_clinical --compact # A/B нового промпта
python exp_cache.py --model gemma4:12b-it-qat        # выигрыш от порядка блоков
```

`run_eval.py` резюмируемый: уже выполненные `(сценарий, модель, стиль)`
пропускаются, поэтому прогон можно прерывать и продолжать — на CPU это
обязательное свойство.

## Что стенд НЕ проверяет

- Клиническую правильность самих порогов пре-классификатора (это вопрос к
  `build_interpretation_flags`, не к нарратору).
- Качество retrieval — для этого в проекте уже есть `eval_retrieval.py`.
- Тон и связность текста: их оценивает человек (или сильная модель) по выборке;
  детерминированные метрики намеренно не пытаются это формализовать.
