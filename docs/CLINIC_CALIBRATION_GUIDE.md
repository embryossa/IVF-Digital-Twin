# Руководство по данным клиники в IVF Digital Twin

> Версия 3.0 · для проекта v7.1
> Инструкция для исследователя — выполняется на компьютере клиники.

---

## Что изменилось в 7.1

В 7.0 это руководство описывало температурную калибровку KAT/GAT/L1 и
динамический τ_KAT (GBDT) из `calibrate_for_clinic.py`, которые вручную
вставлялись в `app.py` и `befe_app.py`. **В 7.1 эти поправки в клинический
расчёт не входят**: они подбирались и проверялись на одних и тех же данных
клиники и не были привязаны к версии моделей. `app.py` больше не загружает
`clinic_adaptation_*.json`, а шаг правки кода из прежнего руководства удалён —
**не вставляйте этот код**.

Клинически применяемая калибровка центра 7.1 — поправка интерсепта логита итоговой
вероятности, проверенная на отобранных одиночных переносах бластоцисты (не менее
100 беременностей, 100 отрицательных исходов и 100 пациенток) и привязанная к
отпечатку моделей. Она реализована в клинической сборке и **не входит в этот
репозиторий**.

---

## Что данные клиники меняют в этом репозитории

| Что | Файл | Влияние на расчёт |
|---|---|---|
| Батчи исходов клиники | `clinic_config.json` | Байесовский posterior L3 (`bayes_mean` в аналитике). **Итог L7 и его диапазон не меняются** |
| OOD-эталон клиники (необязательно) | `models/befe_ood_stats.npz` из `fit_befe_ood.py` | Меняет, какие пациентки отмечаются как OOD, и тем самым точность свидетельств и надёжность в L7 |
| Температура, τ_KAT | `models/clinic_adaptation_*.json`, `gbdt_tau_*.joblib` | Не используется; только исследовательская диагностика калибровки |

## 2. Пошаговый процесс

### Шаг 0 — Получить данные от клиники

```bash
cp ~/Downloads/clinic_data.xlsx data/clinic_data_raw.xlsx
```

### Шаг 1 — Валидация данных

```bash
python validate_clinic_data.py \
    --input  data/clinic_data_raw.xlsx \
    --output data/clinic_data_validated.csv \
    --report data/validation_report.txt
```

Если в отчёте есть `[ERROR]` — исправьте указанные строки в исходном файле и
повторите шаг. Строк с известным исходом меньше 50 — данных недостаточно для
любых выводов о калибровке.

### Шаг 2 — Диагностика калибровки (исследовательская, необязательно)

```bash
python calibrate_for_clinic.py \
    --data   data/clinic_data_validated.csv \
    --clinic "Название Клиники"
```

Скрипт прогоняет строки через модели (первый запуск долгий, 20–40 минут на 250
строк; повторно — с `--skip-inference` по сохранённым предсказаниям) и печатает
ECE до и после температурного масштабирования по слоям. Это показатель того,
насколько модели смещены для данной клиники. Созданный
`models/clinic_adaptation_*.json` в 7.1 ни приложением, ни пакетными скриптами
не применяется.

Температура, подобранная и оценённая на тех же строках, завышает эффект
калибровки. Для выводов оценивайте её на отложенной части данных.

### Шаг 3 — OOD-эталон клиники (необязательно)

Поставляемый `models/befe_ood_stats.npz` (схема 3) описывает обучающую когорту
GAT/KAT: клиника — возраст и КАФ; эмбриология — OCC и эмпирико-байесовские доли
MII/OCC, 2PN/MII, бластоцисты/2PN, с подобранными порогами. `fit_befe_ood.py`
строит эталон по данным клиники в прежней схеме 1: клиника — возраст, АМГ, КАФ,
ИМТ; эмбриология — OCC, MII, 2PN, бластоцисты, KPIScore; пороги χ². Загрузчик
7.1 принимает обе схемы, но это разные детекторы: после замены OOD означает
«нетипично для этой клиники», а не «вне обучающих данных моделей».

1. Сохраните поставляемый файл:
   ```bash
   cp models/befe_ood_stats.npz models/befe_ood_stats.training.npz
   ```
2. В `fit_befe_ood.py` приведите `COLUMN_MAP` к названиям колонок ваших данных.
3. Запустите:
   ```bash
   python fit_befe_ood.py data/clinic_data_validated.csv
   ```
   Если признак в когорте клиники не имеет разброса, подгонка остановится с
   ошибкой: такой детектор отмечал бы как OOD каждую пациентку. Загрузчик тоже
   отклоняет файлы с вырожденным измерением и тогда просто выключает OOD.
4. Верните `COLUMN_MAP` к исходным названиям.

Чтобы вернуться к эталону обучающей когорты — верните сохранённый файл на место.

### Шаг 4 — Обновить `clinic_config.json`

```bash
cp clinic_config.template.json clinic_config.json
```

```json
{
  "clinic_name": "Название Клиники",
  "use_clinic_data": true,
  "batches": [
    [19, 43],
    [15, 38]
  ]
}
```

`batches` — `[беременностей, переносов]` за период (например, квартал). Файл с
реальными исходами клиники в git не попадает.

Батчи входят в байесовский posterior L3 (`bayes_mean` в аналитике и технической
части отчёта). **На итог L7, его диапазон и надёжность они не влияют.**

### Шаг 5 — Перезапуск приложения

```bash
streamlit run app.py
```

Введите тестовую пациентку. В боковой панели должна появиться строка «Данные
клиники активны …», на вкладке L7 BEFE — отметка о состоянии OOD-контроля.

## 4. Периодическое обновление

Раз в квартал: новая выгрузка → Шаг 1 → при необходимости Шаг 3 → Шаг 4.
Данные разных периодов можно объединить:

```bash
python -c "
import pandas as pd
old = pd.read_csv('data/clinic_data_validated.csv')
new = pd.read_csv('data/new_quarter_validated.csv')
combined = pd.concat([old, new], ignore_index=True).drop_duplicates(subset='cycle_id')
combined.to_csv('data/all_data_combined.csv', index=False)
print('Combined:', len(combined), 'rows')
"
```

## 5. Устранение проблем

### `OOD-контроль выключен` на вкладке L7
Нет `models/befe_ood_stats.npz`, файл не совпадает ни со схемой 1, ни со схемой
3, или у него вырожденное измерение. Проверьте командой из раздела 3.

### `OOD baseline: n=0` / `<30 complete rows`
В подпространстве нет полных строк. Проверьте заполнение шаблона
(`validate_clinic_data.py` выдаст детали).

### `ECE before/after одинаковые` (T ≈ 1.0)
Модель уже хорошо откалибрована для этой клиники по данным диагностики.

### Откат к исходному состоянию
```bash
cp models/befe_ood_stats.training.npz models/befe_ood_stats.npz
```
`clinic_adaptation_*.json` на расчёт не влияет, удалять не обязательно.
