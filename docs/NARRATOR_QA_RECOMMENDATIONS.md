# Рекомендации по нарратору IVF Digital Twin

Все пункты — предложения; код проектов не изменялся. Привязка к файлам и
строкам приведена, чтобы можно было применить точечно.

## Если делать только одно

**Дать счётчикам единицу измерения в имени поля** (пункт B2a). Это единственный
дефект, который **переворачивает смысл числа**: ожидаемое число эуплоидных
бластоцист `0.1` озвучено как «вероятность… 0.1%». Стоимость правки —
переименование четырёх ключей.

По влиянию на решение врача найденное делится на три группы:

- **меняет смысл числа** — B2a (единицы);
- **может повлиять на решение косвенно** — потерянный сигнал расхождения
  оценщиков (B3b: BEFE 22.1% против медианы аналогов 61%, раздел выпал);
  введённая моделью тема, которой нет в данных (S11, «внимание на качество
  ПГТ-А»); выдуманный раздел банкинга, создающий впечатление выполненного
  расчёта (C0);
- **портит форму и доверие, но не действие** — snake_case в тексте,
  директивные глаголы, круглые скобки в ссылках, перевёрнутая категория
  согласия, выдуманная причина грейда.

Отдельно стоит **B6**: в английской клинической сборке контроль дозы не
срабатывает вообще (регулярка ищет «МЕ», модель пишет «IU»). Это не про
качество текста, а про отсутствующий предохранитель в поставляемом продукте,
и чинится одним символом класса `(?:МЕ|IU)`. По отношению «польза/стоимость»
это лучшая правка во всём списке.

**Порядок дальнейших правок:**
B2a (единицы) → B6 (регулярка дозы для англ.) → B4 (пустой грейд B) →
C0 (динамический запрос) → B6b (snake_case) → A2 (сжатие гайдлайнов) →
остальное.

## Куда правки лягут

Почти всё — две функции в `llm_consultant.py` (`build_interpretation_flags`,
`build_narrative_context`) плюс `protocol_guidance.build_protocol_guidance`.
Обе функции листовые: их результат читает только нарратор, расчётный контур
(BEFE / CSDI / GAT / номограмма) от них не зависит, поэтому предсказанные
вероятности измениться не могут.

Два предупреждения:
- **`legacy_en_runtime/llm_consultant.py`** — живая англоязычная копия
  (подключается в `legacy_full_report.py:128`, пакуется в
  `scripts/build_bilingual_clinic_release.py:76`). Правки нужно вносить дважды.
- Изменение `build_narrative_context` меняет ключ `llm_cache.make_key(...)` и
  **обнуляет весь дисковый кэш нарративов** — на этом CPU это 12–19 минут на
  каждую переоткрытую пациентку. Правки стоит собрать в один заход.

## A. Производительность на CPU (самое большое)

Замеры этого ПК (i7-8665U, 4 ядра, gemma4:12b-it-qat Q4_0, 100% CPU):
генерация **2.0–2.2 ток/с**, обработка промпта **6.2 ток/с**. Полный нарратив —
**≈19 минут на пациентку**, из них ≈8 минут — только чтение промпта.

### A1. Префикс-кэш на Gemma не работает — и это меняет приоритеты

Первоначальная гипотеза была: переставить блоки промпта так, чтобы инвариантный
корпус гайдлайнов шёл перед переменным блоком пациентки, и тогда llama.cpp
переиспользует KV-кэш общего префикса между пациентками.

**Гипотеза не подтвердилась.** Лог сервера Ollama на реальном прогоне:

```
slot operator(): forcing full prompt re-processing due to lack of cache data
                 (likely due to SWA or hybrid/recurrent memory)
slot operator(): n_ctx_slot = 8192, n_keep = 4, task.n_tokens = 3082, n_swa = 1024
slot operator(): cached n_tokens = 0, memory_seq_rm [0, end)
```

Gemma-семейство использует **sliding-window attention** (`n_swa = 1024`), и
llama.cpp для таких моделей **не умеет переиспользовать частичный префикс**: при
любом расхождении промпта он пересчитывается целиком, с нуля. Порядок блоков
на это не влияет.

Что при этом РАБОТАЕТ — **точное** совпадение промпта: сервер держит снимки
состояния (`cache state: 3 prompts, 2132 MiB`) и восстанавливает их мгновенно.
Замер: повторный идентичный запрос — TTFT **1.4 с вместо ≈490 с**.

Практические следствия:
1. Перестановку блоков делать не нужно — выигрыша не будет.
2. `llm_cache.py` (дисковый кэш по хэшу контекста) — не «приятное дополнение», а
   основной механизм экономии: он ловит ровно тот случай, который ускоряется.
   Повторное открытие пациентки уже мгновенно. Стоит убедиться, что он включён
   в батч-режиме (`DT_LLM_CACHE=1` по умолчанию — да).
3. Единственный оставшийся рычаг для НОВОГО пациента — **сократить сам промпт**
   (пункт A2). Он становится главным, а не вспомогательным.
4. Если батч-режим по десяткам пациенток критичен, префикс-переиспользование
   даст только модель без SWA (например, Qwen/Llama-класс). Это отдельное
   решение с клиническими последствиями (другая модель — другой стиль), и
   принимать его стоит только под измеренную выгоду.

### A2. Сжать блок гайдлайнов

Разбор промпта S03 (3066 токенов):

| блок | токенов | ≈ сек чтения |
|---|---:|---:|
| `protocol_guidance` | 1531 | 246 |
| ↳ из них `гайдлайны` | 1049 | 169 |
| `_SYSTEM_NARRATOR` | 725 | 117 |
| весь остальной клинический контекст | ~600 | ~96 |

5 уникальных источников повторяются **полной библиографией в каждом
утверждении**. Прототип (`compact_ctx.py`) заменяет их коротким тегом
(`ESHRE 2025`) с легендой один раз, ограничивает выдачу 4 утверждениями и
выбрасывает `null`-поля: **−826 токенов ≈ −2.2 мин на пациентку**, в среднем
−47% объёма контекста.

Точки внедрения:
- `protocol_guidance.build_protocol_guidance` (protocol_guidance.py:78) —
  `max_guidelines: int = 8` → 4, и отдавать `citation` коротким тегом;
- `_role` и `инструкция_нарратору` (protocol_guidance.py:132, 148) убрать из
  per-patient контекста — их место в системном промпте, который стабилен.

**Измеренная отдача от этого блока в concise-режиме — низкая.** Из 6 сценариев,
где `protocol_guidance` присутствовал в контексте, раздел «Протокол и
гайдлайны» появился в тексте только в **3**, а ссылки на источники — в двух
(S03 — 6 ссылок, S02 — одна; остальные — ноль). При этом блок стоит ~1050
токенов ≈ 3 минуты ожидания на КАЖДОЙ пациентке, включая те, где он не будет
использован.

Это меняет смысл сжатия: речь не только об экономии, но и о том, что дорогой
RAG-слой в быстром режиме почти не доходит до читателя. Варианты:
- отдавать `protocol_guidance` только в стиле `narrative` (где он реально
  используется), а в `concise` — не класть вовсе: −1050 токенов ≈ −3 мин;
- либо оставить 2–3 самых сильных утверждения и потребовать ссылку явно.

Оговорка: там, где раздел всё же появился, он выполнен **безупречно** —
доза во всех трёх случаях приведена полным диапазоном номограммы
(100–150, 225–300, 150–225 МЕ) и с правильной рамкой «ориентир по номограмме»,
без единого отклонения. Проблема не в качестве, а в том, что это происходит
в половине случаев.

Как строить короткий тег — есть готовый ответ. В `guidelines_pack.json` ключи
`_meta.sources` уже являются компактными идентификаторами: `ESHRE2025`,
`ASRM2023`, `BFS2024`, `POSEIDON2016`, `InverseFSH2021`. Сейчас
`guideline_rag._format_statement` (guideline_rag.py:70) заменяет `source` на
полную библиографию и сам ключ теряет. Достаточно оставить **и** `source`
(ключ), **и** `citation`: нарратору давать ключ, легенду с полными
библиографиями показывать в UI/отчёте один раз.

Важно: это не тот случай, из-за которого раньше убирали `id` утверждения
(коммент `[FIX]`, protocol_guidance.py:120). Там протекал внутренний
идентификатор вида `ASRM_agonist_trigger` — нечитаемый для врача. Ключ источника
`ASRM2023` — нормальная человеческая ссылка.

Перед этим стоит поправить сам корпус: ключ `ASRM2023` указывает на публикацию
`Fertil Steril 2024;121:230-245`, то есть год в ключе и год в цитате
расходятся. Если ключ станет отображаемым тегом, это расхождение станет видно
врачу. Аналогично ключ `Arce` без года.

### A2a. Стиль по умолчанию — самый дорогой, и он длиннее заявленного

UI ставит стиль `narrative` первым в радио-кнопке (app.py:2878), то есть по
умолчанию. Подсказка обещает «~400 слов»; замер дал **592 слова / 1262 токена**
— в полтора раза больше, то есть +2.5 минуты генерации сверх ожидаемого.
`concise` дал 142–206 слов при том же уровне соблюдения правил (а по утечкам
сырых ключей местами даже лучше).

Предложение: сделать `concise` дефолтом, `narrative` — осознанным выбором;
и привести текст подсказки в соответствие с фактической длиной.

### A3. Не гонять 12B там, где хватает 4B

`DT_LLM_NARRATOR` по умолчанию `medgemma1.5` (4.3 ГБ) — верное решение для CPU;
`gemma4:12b-it-qat` (8.8 ГБ) на этом железе примерно втрое дороже. Рекомендация:
оставить 12B как осознанный выбор пользователя в UI, но в **батч-режиме**
(десятки пациенток подряд) по умолчанию использовать 4B-класс.

### A4. Таймаут по умолчанию проходит впритык к реальному времени ответа

`_TIMEOUT_READ = 1200` с (llm_consultant.py:34) — а измеренный полный нарратив на
этом ПК занял **1124 с**. Запас 6%. Чуть более длинный контекст, чуть более
разговорчивый ответ или фоновая нагрузка — и блокирующий `consult()`
(llm_consultant.py:1074) поймает `requests.exceptions.Timeout`, который
обрабатывается вместе с `ConnectionError` и возвращает `_OFFLINE_MSG`:
«Локальная LLM недоступна (Ollama не запущена…)». Сообщение вводит в
заблуждение — Ollama работает, она просто не успела.

Предложения:
1. Развести обработку: `Timeout` → «модель не успела за N секунд, попробуйте
   style='concise' или модель полегче», `ConnectionError` → текущее сообщение.
2. Поднять дефолт `DT_LLM_TIMEOUT_READ` для CPU-профиля до 1800–2400 с либо
   выводить его из замеренной скорости.
3. Предпочитать потоковый путь (`consult_stream`) и в скриптах/батче, а не
   только в UI: при стриминге read-таймаут отсчитывается от последнего
   полученного чанка, а не от начала запроса, поэтому длинная генерация его не
   провоцирует. В наших прогонах именно потоковый режим отработал стабильно.

## B. Корректность и безопасность вывода

### B1. `faithfulness.py` не проверяет цитаты в круглых скобках

`_BRACKET = re.compile(r"\[([^\[\]]{2,120})\]")` (faithfulness.py:24) ищет только
**квадратные** скобки. Модель в наблюдённых прогонах выводит источники в
круглых — и вся первая половина проверки (утечка внутренних id, неизвестные
ссылки) молча не срабатывает, а отчёт возвращает `ok`. Это ложное чувство
защищённости: механизм есть, но на реальном выводе не работает.

Две части исправления, нужны обе:
1. в `_SYSTEM_NARRATOR` потребовать ссылки **в квадратных скобках**
   (`[ESHRE 2025]`) — тогда проверка включается;
2. в `faithfulness.py` дополнительно разбирать круглые скобки, содержащие
   год или акроним, — на случай, если модель всё-таки отступит от формата.

### B1a. Результат проверки достоверности не доходит до врача

`consult_stream` (llm_consultant.py:1168) вызывает `check_faithfulness` и кладёт
результат в `_audit_log` — и на этом всё. Если проверка нашла дозу вне
номограммы или выдуманный источник, врач видит обычный текст без единого
признака проблемы, а запись уходит в `dt_analytics_data/llm_consult_log.jsonl`,
куда никто не смотрит в момент приёма. Предложение: при `faithfulness.ok == False`
показывать в UI видимую плашку («в тексте есть число дозы вне диапазона
номограммы — сверьтесь с блоком протокола») и в батч-режиме помечать такие
записи в отчёте. Проверка уже написана и стоит миллисекунды — не хватает только
вывода наружу.

### B2. Числа заземлены, но приписаны не тому полю

Класс ошибок, который проверка «числа только из JSON» не ловит принципиально.
Наблюдение: для ближайшего GAT-аналога модель написала «получение **5 зрелых
ооцитов**», тогда как у соседа `MII = 7`, а `5` — это его `2PN`. Число из
контекста, правило формально не нарушено, врач вводится в заблуждение.

Предложения:
- в промпт: «число ставь рядом с тем полем, откуда оно взято»;
- в стенд: проверка `label_binding` (реализована) — сверяет число рядом с меткой
  со значением именно этого поля, а раздел аналогов — против профиля соседа.

### B2a. Счётчик подан как процент — потому что в имени поля нет единицы

Наблюдение (S02, 41 год, AMH 0.6). Контекст: `banking_mii.euploids_expected: 0.1`
— это **ожидаемое ЧИСЛО эуплоидных бластоцист** (0.1 эмбриона из медианного
выхода MII). Модель написала:

> «…при крайне низкой **вероятности** получения эуплоидных эмбрионов в текущем
> цикле (**0.1%**)».

Число из контекста, правило «числа только из JSON» формально соблюдено, а смысл
искажён радикально: 0.1 эмбриона превратилось в 0.1% шанса.

Причина системная. В `build_narrative_context` поля названы так, что единица
угадывается только для процентов (`P_pct`, `CI_low_pct`), а счётчики идут голым
числом: `euploids_expected`, `MII_this_cycle`, `mii_target_80pct`,
`cycles_for_P50`. При этом прежний `build_clinical_context` нёс рядом
текстовые `пояснение`, где единицы проговаривались словами — при переходе на
компактный контекст эти пояснения выпали.

Предложение (дёшево, ~10 токенов): дать счётчикам суффикс единицы —
`euploids_expected_n`, `MII_this_cycle_n`, `cycles_for_P50_n`,
`mii_target_80pct_n`. Тогда модели нечего угадывать. В стенде это ловит
метрика `UNI` (`unit_confusion`).

### B3. Блок аналогов потерял предупреждение при переходе на компактный контекст

`build_clinical_context` (llm_consultant.py:651) отдавал соседей вместе с
пояснением: «GNN_P_беременность — прогноз модели для СОСЕДА (не пациентки)».
В `build_narrative_context` (llm_consultant.py:490) остались только числа —
пояснение не перенесено. Наблюдаемое следствие: «Это подтверждает ожидаемую
динамику для данного профиля» — вывод о пациентке из прогноза для другого цикла.
Стоит вернуть одну строку-пояснение (≈25 токенов) либо закрыть это правилом
в системном промпте.

### B3a. Клинически бессмысленные экстраполяции попадают в контекст без ограничителя

S04 (44 года, AMH 0.2, AFC 2): контекст отдаёт `cycles_for_P50: 25`,
`cycles_for_P70: 50`, `mii_target_80pct: 89`. Нарратор честно пересказывает:
«для достижения вероятности 50% может потребоваться **до 25 циклов**».
Число арифметически верно (`ceil(1 / 0.04)`), но как клиническое утверждение
оно бессмысленно: 25 стимуляций никто не проводит, а формулировка выглядит как
план действий.

В `build_clinical_context` для обратной таблицы MII такой ограничитель есть —
там пишется `"более 200"` (llm_consultant.py:724). В `build_narrative_context`
для `cycles_for_P50/P70` его нет.

Предложение: в `build_narrative_context` (llm_consultant.py:454–477) обрезать
`cycles_for_*` разумным потолком и отдавать метку вместо числа, например
`"> 6 — накопление в рамках разумного горизонта недостижимо"`. Тогда нарратор
скажет то, что действительно нужно врачу, а не приведёт нереализуемый план.

### B3b. В concise-режиме блок GAT-аналогов оплачивается, но не доходит до врача

Наблюдение: из трёх concise-прогонов, где `historical_analogues` присутствовал в
контексте (S01, S02, S09), раздел про аналоги не появился в тексте **ни разу**.
Блок стоит ~130 токенов промпта (~23 с на этом ПК) и не используется.

Особенно важно это в S09: BEFE даёт 22.1% («низкий»), а медиана GAT-соседей —
61%. Расхождение втрое — это содержательный сигнал о неопределённости, и он
молча теряется. Формально модель поступила правильно (не переклассифицировала
прогноз), но врач не узнал о расхождении вовсе.

Два возможных решения, выбор за владельцем:
1. если аналоги нужны — вынести расхождение в **вычисляемый флаг**
   (`analogues_vs_forecast: "аналоги выше прогноза на 39 пп"`), тогда он попадёт
   в текст как факт, а не как раздел, который можно опустить;
2. если не нужны — не класть `historical_analogues` в concise-контекст и
   сэкономить время.

Первый вариант предпочтительнее: расхождение оценщиков — именно то, что врач
должен видеть, и оно вычисляется в Python одной строкой.

### B4. `confidence_grade = "B"` при полном отсутствии доказательств

`build_interpretation_flags` (llm_consultant.py:282): когда BEFE отсутствует,
`ci_cat` и `agr_cat` равны `""`, `rel is None`, и условие
`ci_cat != "high_statistical_uncertainty" and agr_cat != "high_model_disagreement"
and (rel is None or rel >= 35)` истинно → грейд **B**.

То есть пациентка, по которой нет ни ансамбля, ни ДИ, ни OOD-статуса, получает
«умеренную надёжность», и нарратор обязан это объяснять читателю. Предложение:
ввести явный исход `insufficient_evidence` (или `None`), когда нет ни
`CI_category`, ни `agreement_category`, ни `reliability`.

**Подтверждено на прогоне (S07).** Контекст: `grade: "B"`, все под-поля `null`.
Нарратор выдал: «Уровень уверенности составляет Grade B. **Модель демонстрирует
стабильность**». Дефект пре-классификатора дошёл до врача как утверждение о
стабильности модели, которой не существует. Это не ошибка LLM — она честно
объяснила то, что ей дали.

### B4a. Пороги Tier 0 и Tier 1 разошлись после рекалибровки

`build_interpretation_flags` был осознанно перекалиброван (комментарий `[CALIB]`,
llm_consultant.py:239–248): границы согласия ансамбля подняты с 10/20 до
**15/30 пп**. В системном промпте аналитика Tier 1 (`_SYSTEM_ANALYST`,
llm_consultant.py:1225) осталось старое правило: «< 10 пп = высокая, 10–20 =
средняя, > 20 = низкая». Тот же разброс теперь описывается двумя вкладками
по-разному: при spread = 12 пп Tier 0 скажет «высокое согласие моделей», а
Tier 1 — «средняя согласованность»; при 25 пп — «умеренное» против «низкая».

Там же расходится порог пустого цикла: правило 7 Tier 1 — «> 30%», флаги Tier 0 —
35% / 20%.

Ширина ДИ (правило 6, < 15 / 15–30 / > 30) с флагами совпадает — то есть при
рекалибровке синхронизировали одну константу из трёх. Предложение: вынести
пороги в один модуль-источник и подставлять их в оба промпта, чтобы правка в
одном месте не оставляла второй текст рассинхронизированным.

### B4b. Грейд передаётся без причины — и нарратор причину выдумывает

Наблюдение (S04): «Конфидентность уровня C обусловлена умеренной статистической
неопределённостью и **несогласием моделей** (agreement: moderate)».

Здесь сразу две ошибки. Во-первых, `moderate_model_agreement` (разброс 24.3 пп)
пересказано как «несогласие» — прямо рядом с процитированной противоположной
меткой. Во-вторых и важнее: грейд C у этой пациентки выставлен ветвью
**двойного OOD** (`ood_clinical and ood_embryology`, llm_consultant.py:274), а
вовсе не разбросом ансамбля. Модель сконструировала причинную связь сама.

Это не лечится промптом: `build_interpretation_flags` **знает**, какая ветвь
сработала, но наружу отдаёт только букву. Предложение — отдавать причину рядом
с грейдом:

```python
flags["confidence_grade"] = "C"
flags["confidence_grade_reason"] = "dual_subspace_OOD"   # | "low_reliability"
                                                          # | "wide_CI" | "model_disagreement"
```

и в `prediction_confidence` контекста добавить это поле. Тогда нарратор
объясняет реальную причину, а не правдоподобную. Стоимость — 5 строк и ~8
токенов промпта.

### B5. Выбрасывать `null`-поля из контекста нарратора

`response_phenotype: {label: null, confidence_pct: null}`,
`prediction_confidence` со всеми `null`, `patient.amh_ng_ml: null` — попадают в
промпт как есть. Это одновременно лишние токены и приглашение домыслить.
Рекурсивная чистка (`_prune` в `compact_ctx.py`) снимает вопрос.

### B6. Английская сборка защищена слабее русской — три эффекта сразу

Это не про качество текста, а про то, что в двуязычном клиническом релизе
(`scripts/build_bilingual_clinic_release.py`) английский нарратор работает с
заметно более слабыми ограничителями. Три независимых наблюдения складываются:

**1. Проверка дозы физически не может сработать.** `faithfulness.py:27–28`:

```python
_DOSE_RANGE  = re.compile(r"(\d{2,3})\s*[–—-]\s*(\d{2,3})\s*МЕ")
_DOSE_SINGLE = re.compile(r"(?<![–—\-\d])(\d{2,3})\s*МЕ")
```

Единица — кириллическое «МЕ». Английский нарратор пишет «150–225 IU».
`legacy_en_runtime/llm_consultant.py:1080` честно вызывает
`check_faithfulness`, тот не находит ни одного совпадения и возвращает `ok`.
То есть **для английской сборки контроль дозы отсутствует полностью**, при
этом в логе выглядит как пройденный.

**2. Системный промпт вдвое-втрое короче и без ключевых правил.** Русский
`_SYSTEM_NARRATOR` — 2154 символа: нумерованные правила, разделы, отдельный
блок про дозу («Дозу подавай только как ориентир… Числа дозы бери исключительно
из этого блока»). Английский (`legacy_en_runtime/llm_consultant.py:527`) — один
абзац ~600 символов, в котором про дозу нет ничего, кроме
«protocol/guidelines only if present». При этом блок `protocol_guidance` с
числами дозы английскому нарратору передаётся (там же, строка 513).

**3. Грунтинг на другом языке.** Ключи блока и тексты корпуса — русские
(`номограмма`, `стартовая_доза_МЕ`, «Конвенциональной считается суточная доза
FSH 150-225 МЕ…»). Английская модель должна извлечь из русского источника
английское утверждение — лишняя степень свободы там, где её быть не должно.

Предложения по возрастанию стоимости:
1. в `faithfulness.py` сделать единицу дозы вариативной:
   `(?:МЕ|IU)` — одна правка, снимает самый острый пункт;
2. довести английский `_SYSTEM_NARRATOR` до паритета с русским (перевод уже
   существующих правил, новых сущностей не требуется);
3. добавить в `guidelines_pack.json` параллельное поле `text_en` и отдавать его
   при английской локали — корпус небольшой (29 утверждений).

### B6a. Готовая спецификация стиля не подключена к коду

В корне проекта лежит `SYSTEM_NARRATOR_v2.md` (15.8 КБ) — подробный стилевой
регламент с парами «плохо / хорошо», словарём вероятностей и правилами
интерпретации ширины ДИ. Его собственный заголовок гласит: «Вставить в
llm_consultant.py как значение переменной `_SYSTEM_NARRATOR`». Поиск по коду
показывает, что этого не произошло: продакшн использует короткий вариант v3
(2154 символа), в котором указаний по стилю нет вовсе.

Именно этим объясняется канцелярит в наблюдённых текстах («В связи с этим»,
«Данный подход», «Ключевым аспектом данного случая является») — ровно те
обороты, которые v2 запрещает своими примерами.

Полностью подключать v2 на этом железе не стоит: 15.8 КБ ≈ 5300 токенов ≈
+15 минут на пациентку. Разумный компромисс — перенести в рабочий промпт только
раздел «КАК ПИСАТЬ» в сжатом виде (5–7 строк, ~120 токенов ≈ 20 секунд), а сам
файл оставить как справочник.

### B6b. Технические метки в тексте для врача

Модель регулярно вставляет `high_model_agreement`, `in_distribution`,
`immediate_transfer_feasible`, `standard_responder` прямо в текст вместо
клинической формулировки. Лечится одной строкой промпта («никакого snake_case в
тексте врача»); стенд считает это метрикой `LEAK`.

## C. Промпт

### C0. Запрос пользователя противоречит системному правилу «пропускай без данных»

`_DEFAULT_QUESTION` (llm_consultant.py:928) — статическая строка, которая всегда
просит «…исторические аналоги GAT, природа неопределённости ансамбля…».
`_QUESTION_CONCISE` (llm_consultant.py:935) — «…неопределённость ансамбля
количественно». Но у части пациенток блоков `historical_analogues` и
`prediction_confidence` в контексте нет вообще (GAT не отработал, BEFE не
посчитан). Получается прямой конфликт: системный промпт велит молчать о том,
чего нет, а пользовательское сообщение — идущее последним и потому более
«свежее» для модели — явно требует эти разделы.

**Подтверждено на прогоне (S07).** В контексте нет блока `banking_mii` вообще.
Модель всё равно написала раздел «Банкинг MII»:

> «В данном случае стратегия банкинга требует оценки соотношения вероятности
> получения эуплоидных эмбрионов и темпов снижения овариального резерва с
> учётом возраста.»

Ни одного числа — формально правило «числа только из JSON» не нарушено. Но
раздел создаёт у врача впечатление, что расчёт банкинга выполнен, тогда как его
не было. Ровно то, что просил `_QUESTION_CONCISE`: «логика банкинга одной
фразой».

То же повторилось в S11 («логика банкинга может быть направлена на
максимизацию количества эуплоидных эмбрионов») — **2 из 2 сценариев без блока
`banking_mii` получили выдуманный раздел банкинга.** Это воспроизводимый
дефект, а не случайность генерации.

Предложение: собирать запрос динамически из фактически присутствующих ключей
контекста (5 строк кода). Это снимает конфликт, экономит токены и убирает
самый частый повод для выдуманного раздела.

### C1. Инвертированная пирамида вместо линейных 9 разделов

На 2 ток/с первые 60 токенов появляются через ~30 секунд, а последний раздел —
через 10–19 минут. Сейчас «Итог» стоит восьмым, то есть главный вывод врач
получает последним. Предложение: раздел «Суть» (3–4 предложения) первым — врач
получает клинический ответ за полминуты, остальное дочитывает при желании.
Стоимость изменения — ноль токенов, выигрыш по воспринимаемой задержке — 20–30×.

### C2. Правила, перенесённые из lead-analyst

Из реального выхода `lead_analysis.md` переносимы дёшево:
- разделять факт (из JSON) и гипотезу (механизм, причина);
- значение у границы категории называть **пограничным**, а не провальным, и
  использовать ДИ как квалификатор («нижняя граница не дотягивается до порога»);
- прямо проговаривать, чего система не знает.

### C3. Конфликт правила 3 с текстом самих гайдлайнов

Системный промпт запрещает «рекомендуется/следует», а извлечённые утверждения
ESHRE/ASRM написаны именно так («следует рассматривать», «рекомендуется
рассмотреть»). Модель оказывается между двумя инструкциями. Стоит разрешить явно:
цитату гайдлайна приводить как есть, от своего лица директив не давать.

## D0. В аналитике `confidence_grade` — константа. Проверено на 467 реальных циклах

Это не про нарратор DT и не про синтетику: дефект сейчас работает в
продакшене embryo-lab-data.

**Факт.** Во всех трёх сохранённых бандлах у **каждого** пациента
`confidence_grade = "B"`:

| когорта | n | грейдов «B» | из них без единого CI-сигнала |
|---|---:|---:|---:|
| `data/processed` | 18 | 18 | 18 |
| `data/processed/ggrc` | 225 | 225 | 225 |
| `data/processed/fertimed` | 224 | 224 | 224 |

467 из 467. Поле не несёт информации — это константа, которую `dt-narrator`
добросовестно объясняет врачу как результат оценки.

**Механизм — рассогласование имён колонок, а не отсутствие данных.**
`consult.build_flags` (src/embryo/consult.py:39, 47) ищет:

- для ДИ — `bayes_ci_low` / `ci_kat_low` / `bayes_ci_high` / `ci_kat_high`;
- для разброса — `p_per_transfer`, `bayes_mean`, `p_kat_raw`, `p_nvsa`,
  `p_csdi`, `p_gnn_ens`, `DIGITAL TWIN`.

А в бандле реально присутствуют ровно три числовых поля: **`DIGITAL TWIN`,
`PRAI`, `ci_width_pp`**. Все остальные — `None`. Поэтому:

- `CI_category` не вычисляется никогда, хотя **`ci_width_pp` лежит рядом и
  просто не читается**;
- `agreement_category` не вычисляется никогда, потому что из семи искомых
  оценщиков заполнен один. **`PRAI` в список не входит** — хотя это второй
  независимый оценщик, присутствующий у каждого пациента.

Дальше срабатывает та же ветка с пустыми строками, что и в DT
(src/embryo/consult.py:60): `"" != "high_statistical_uncertainty"` истинно →
грейд «B».

**Внутреннее противоречие.** В когорте fertimed сам пайплайн помечает
**138 из 224** циклов как `ci_wide = True` (там `ci_width_pp` ненулевой у 176
записей) — и одновременно отдаёт нарратору по ним «B, умеренная надёжность»,
без категории ДИ вообще.

**Что это значит для отчётов.** Инструкция `dt-narrator` требует объяснить
грейд A/B/C и «разделить статистическую неопределённость = ширина CI и
модельную = разброс ансамбля». Ни ширины CI, ни разброса в пакете нет, а грейд
одинаков у всех — то есть агент по построению не может выполнить свою
инструкцию и вынужден писать одно и то же для каждой пациентки.

**Исправление — три небольших правки в `build_flags`:**

1. читать готовое `ci_width_pp` напрямую, а не только выводить из `ci_low/ci_high`;
2. добавить `PRAI` в список оценщиков для разброса (тогда пара DT↔PRAI даёт
   реальный сигнал: по ggrc медиана расхождения 4.9 пп, максимум **61.6 пп** —
   а 61.6 пп это уже `high_model_disagreement`, который врачу важно видеть);
3. если после этого обоих сигналов всё равно нет — отдавать
   `insufficient_evidence`, а не «B» (та же правка, что B4 в проекте DT).

Порядок важен: без пункта 3 когорты, где `ci_width_pp = 0` у всех (ggrc и
`data/processed`), просто сменят одну константу на другую — грейд станет «A»
вместо «B». Нулевая ширина ДИ у 100% циклов — это отдельный вопрос к тому,
доезжает ли CI от TabPFN/PRAI для этих клиник, и его стоит посмотреть
независимо.

## F. Направления развития (не починка, а следующий шаг)

### F1. Числа ставит Python, связки пишет модель

Самая сильная идея, вытекающая из всех находок. Сейчас принцип звучит как
«Python классифицирует — LLM объясняет», но **числа всё ещё набирает модель**,
и именно там возникли путаница единиц (0.1 эмбриона → «0.1%») и приписывание
числа не тому полю (2PN → «зрелые ооциты»).

Логичное продолжение принципа: числовые утверждения собирать шаблоном в Python,
а модели оставить только связующий текст. Например, Python формирует готовые
фразы-факты:

```
"вероятность беременности на перенос — 22.1% (95% ДИ 18.1–26.4)"
"ожидается 0.4 эуплоидной бластоцисты за цикл"
"по номограмме стартовая доза — 225–300 МЕ"
```

а модель получает их как **неизменяемые строки** с задачей связать в нарратив.
Тогда класс ошибок «неверная единица / неверная привязка» исчезает
конструктивно, а не вероятностно. Это дешевле по токенам, чем нынешний JSON,
и снимает нагрузку с правил промпта.

### F2. Двухуровневая генерация: 4B по умолчанию, 12B по флагу

На CPU разница между 4B и 12B — это разница между 4 и 12 минутами. Но
подавляющее большинство случаев тривиальны для нарратора: «стандартный ответ,
грейд A, рисков нет». Разумная схема: 4B пишет всех, а на 12B (или в облако)
эскалируются только случаи, где цена ошибки выше — грейд C, OOD, высокий риск
СГЯ, расхождение линз СГЯ, провал `faithfulness`. Правило эскалации
вычисляется из уже существующих флагов, новых сущностей не требуется.

### F3. Предгенерация для аналитического пайплайна

В связке с embryo-lab-data нарративы нужны для review-list — это офлайн-задача
без человека в ожидании. Прогонять их пакетно (ночью), складывая в
`llm_cache` по хэшу контекста; к моменту разбора тексты уже готовы и открываются
мгновенно. Это снимает проблему 12 минут полностью — но только для аналитики,
не для интерактивного приёма.

### F4. Показывать врачу результат самопроверки

Стенд считает 9 метрик за миллисекунды и без обращения к модели. Ничто не мешает
гонять подмножество из них (`unit_confusion`, `null_safety`, `label_binding`,
`faithfulness`) прямо в `consult_stream` после генерации и показывать плашку
при срабатывании. Врач получает не только текст, но и признак того, что текст
прошёл автоматическую сверку с данными — при работе с локальной моделью это
существенная часть доверия.

### F5. Расширить обмен между двумя проектами

Подробно — в `NARRATOR_VS_ANALYTICS.md`. Кратко: DT уже вычисляет для каждого
цикла ширину ДИ, разброс ансамбля, OOD-статус и подобранные гайдлайны, но в
аналитический пакет (`src/embryo/consult.py:100`) ничего из этого не попадает.
В обратную сторону: у аналитики есть фактический исход цикла, которого нет у DT.
